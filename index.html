Overview

A unified web, mail and network operations case study

This portfolio describes a sanitized infrastructure project that brought together a corporate website, Linux-based hosting, managed mail services, reverse proxying, secure external access, routed internal access, DNS authentication, backup planning and operational troubleshooting.

Centralized web and mail services under a maintainable operating model.
Enabled secure internal and external access without publishing production identifiers.
Established encrypted connectivity between infrastructure locations.
Created repeatable validation, backup and recovery documentation.

Challenge

Balancing public delivery, internal reliability and mail control

The organization needed a maintainable platform for website delivery and corporate email while supporting different access paths for internal and external users. The architecture also needed practical security controls, reliable DNS and email authentication, and recovery procedures that could be used during incidents.

Public website delivery

The platform needed to serve a corporate website through a controlled hosting path with HTTPS and reverse proxy awareness.

Mail access patterns

Internal and external users needed reliable access to SMTP, IMAP and webmail without exposing unnecessary infrastructure detail.

Outbound routing control

Different hosted domains required direct and relayed outbound SMTP concepts while keeping DNS authentication aligned.

Design Decisions

Why the platform was shaped this way

The implementation favored maintainable operational boundaries: public access through controlled edges, mail authentication through DNS records, internal access through routed paths, and public documentation through sanitized abstractions.

Use established services instead of custom mail or routing software.
Keep public web delivery, mail transport and internal access responsibilities distinct.
Document concepts without exposing hostnames, addresses, mailbox data or secrets.
Validate changes with repeatable checks before treating the system as healthy.

Mail Platform

Corporate email services with controlled delivery paths

Mail operations included Exim SMTP, Dovecot IMAP, Roundcube webmail, TLS access, internal and external mailbox access, relay integration and domain-based outbound mail routing concepts.

Inbound mail was coordinated through public DNS, MX concepts and a Linux-based mail server.
Exim handled SMTP submission and transport while Dovecot provided IMAP mailbox access.
Roundcube provided browser-based webmail for users who needed a managed web interface.
Outbound mail could use direct or relayed paths depending on the hosted domain policy.
SPF, DKIM, DMARC, MX and PTR concepts were documented as part of deliverability and trust.

Connectivity

Secure external entry and internal routed access

A European VPS provided a controlled external entry point. HAProxy and SMTP relay behavior were integrated with an encrypted WireGuard path toward the internal edge router, where firewall, NAT and policy-based routing decisions were maintained at a high level.

External entry point

A European VPS acted as a sanitized public edge for selected access paths.

Encrypted tunnel

WireGuard provided a secure site-to-site transport concept between infrastructure locations.

Edge routing

MikroTik RouterOS handled firewall, NAT and policy-based routing responsibilities.

Service relay

HAProxy and SMTP relay behavior supported controlled external access and outbound delivery.

Mail and Network Routing

Controlled paths for users, domains and services

Routing was documented as a set of responsibilities rather than public configuration. The portfolio distinguishes internal access, external access, reverse proxy behavior, relay behavior and domain-specific outbound mail handling.

Internal users reached services through routed internal paths.
External users reached selected services through a controlled public edge.
Reverse proxy behavior separated public entry from backend service placement.
Domain policy determined whether outbound SMTP used direct or relayed delivery.
DNS records supported mail trust while avoiding disclosure of production values.

Recovery

Troubleshooting, incident recovery and validation

The recovery story is documented as a generalized operational process: symptoms, investigation, root cause category, restoration, validation and preventive documentation. It avoids real logs, command history, hostnames or incident identifiers.

Symptoms were documented from user-visible behavior and service health checks.
Investigation separated website files, control panel files, mail services and routing layers.
Root cause category: hosting control panel application dependencies became unavailable after a filesystem-related change.
Recovery focused on restoring required application files, validating services and avoiding unrelated changes.
Preventive actions emphasized backup verification, path validation and clearer recovery notes.

Lessons Learned

Operational lessons from hybrid infrastructure work

Separate production configuration from public documentation.
Test restore procedures, not only backup creation.
Treat control panel files separately from hosted website files.
Validate filesystem paths before destructive operations.
Keep network and mail routing documentation current.
Use explicit health checks after infrastructure changes.
Protect keys and credentials from version control.
Use staged changes for critical mail systems.
Verify DNS, TLS and routing together.
Keep public portfolio material sanitized.
